# Engineering principles

Use TDD for application changes: choose public behavior, write and run a failing test, implement the smallest complete change, then verify it passes before the next slice. Test browser workflows and HTTP interfaces against isolated real PostgreSQL schemas. Cover persistence, validation, access isolation and failure paths. Preserve existing regressions; update assertions only when an approved behavior changes.

Keep responsibilities separate: React presents data and captures intent; HTTP modules resolve identity and validate requests; domain/storage modules enforce ownership and persistence. Use explicit typed contracts, parameterized SQL, dependency injection at external interfaces, and cohesive modules with small public surfaces. Prefer composition and straightforward code over speculative abstractions. Follow SOLID principles where they reduce coupling and clarify ownership.

Server-resolved identity and active department membership are authoritative. Never accept ownership or role grants from client input. Preserve history and department scope when membership ends, except for explicitly requested data removal under the policy below. Keep local access explicitly configured and unavailable by default; production requires authenticated sessions.

For prototype additions or refinements, read `prototype/AGENTS.md` in the retained prototype worktree `/home/jacobuntu/Ops/worktrees/lantern-ui-prototypes`. Application code must not depend on prototype files or expose prototype controls.

Distinguish `planned`, `applied` and `failed`; never infer execution from script preparation. Agents must not request sensitive production output as proof.
4. If the changelog entry cannot be prepared, routine operations wait. Jaco may use the emergency exception only to stop an active exposure of private data, prevent imminent data loss, or restore an outage that cannot reasonably wait for the normal process. Convenience, routine corrections and dogfooding enrollment do not qualify. Jaco decides whether the criteria apply, keeps a minimal secure note recording the justification, and completes the sanitized changelog, outcome review and access cleanup once the situation is stable. No second reviewer is required. This exception never grants an agent production access.

Keep reusable scripts, procedures and the sanitized operational changelog in the repository so investigating agents can understand production changes. Exclude names/emails of affected people, person-linked record identifiers, conversation content, credentials and sensitive SQL values from entries, reasons, scripts and evidence. Use general descriptions such as "Corrected a membership assignment." Only retain a separate private supplementary record when necessary sensitive details warrant retention; keep those details outside Git and agent context. Retain the sanitized operational changelog for the lifetime of the repository, including archival. Correct inaccurate entries transparently; preserve the distinction between planned and executed changes. The repository-lifetime rule applies only to sanitized history, not conversation data, backups or private supplementary records; member-requested removal follows the rule above. If sensitive information enters Git, treat it as an incident; deleting it from the current file alone does not remove it from history. This operational record does not require a PR or an organizational Changelog submission; do not submit one automatically. Repository history provides traceability, not a tamper-proof audit system.
