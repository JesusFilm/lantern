# Independent review gate

Every pull request into `main` gets an automated review published as the required check **Independent review**. The check is the enforcement mechanism; it is not a formal pull request approval.

## How it works

[independent-review.yml](../../.github/workflows/independent-review.yml) runs on `pull_request_target`, so it executes the workflow and harness from `main`, never code from the pull request. It never checks out or runs pull request code. [tools/review](../../tools/review) mints a short-lived installation token for the **Lantern Independent Review** GitHub App (Checks write, Pull requests write, Contents read, this repository only), reads the change through the API, asks the AI gateway for a strict JSON verdict, and publishes the check on the exact head SHA.

- The check opens `in_progress`, then completes as `success` or `failure`; neutral, skipped and cancelled are never produced.
- Fail closed: a missing, empty or oversized diff, unreviewable content (below), unreadable guidance, a gateway error or truncation, a malformed verdict, or a verdict with any blocker or major finding completes the check as `failure`. If the check cannot be opened or completed, the job fails.
- **Triggers.** A pull request opened, reopened, marked ready for review or retargeted to `main` is reviewed, as is every push. Retargeting emits `pull_request_target` `edited` with `changes.base`, which the workflow subscribes to; an `edited` event without a base change (a title or body edit) starts no review, and its concurrency group is unique to that run so it cannot cancel a review in progress. A pull request retargeted away from `main` is not reviewed. `tools/review/workflow.test.mjs` evaluates the workflow's own expressions for each event.
- A new push gets a fresh review. The review is bound to a fixed range: the diff and file list are fetched from the compare API by the base SHA and head SHA read at the start (`base...head`), never from the moving pull request, so a push during the run cannot change what was reviewed. After the model answers, the harness re-reads the pull request; if the head is no longer the reviewed SHA, the pull request is closed, or the re-read fails, a passing verdict is discarded and the check completes as `failure` ("Head moved or could not be verified").
- **Unreviewable content fails closed before the model is called.** The diff is read as raw bytes and decoded as strict UTF-8; a diff containing NUL bytes or invalid UTF-8 is rejected, because decoding with replacement could turn corrupted content into text the model approves (a genuine U+FFFD character is valid UTF-8 and is accepted). The diff text is cross-checked against GitHub's file list, which is fetched separately. For every file the hunks sent to the model must match the patch GitHub lists, and the additions, deletions and total must equal the counts GitHub lists, so a diff cut between complete hunks, or altered, cannot pass. The comparison is exact: same number of patch lines, same kind of each line, identical hunk headers and counts, and identical text, invisible characters included (only a trailing newline is ignored), so `admin` and `ad` plus a zero-width space never compare equal. Binary files, files with no patch, any file mode change (including a rename or edit that also changes the mode), files present in only one of the two, and file lists of 100 or more entries (possibly truncated) fail the check, and the summary lists them. Such a change needs the owner's decision outside this gate. The only allowances are a pure rename (no content or mode change) and an empty new or deleted file, both disclosed to the model. A pure rename has no patch, so its full head content is provided like any modified file, with the same size checks and a failure if it is unavailable: a dormant file moved into `.github/workflows/` is reviewed as new content.
- **Context, and when it is sufficient.** Trusted guidance is read from the base commit, never the head: `AGENTS.md` (required; a missing or unreadable file fails the check), then `CONTEXT.md`, `GLOSSARY.md` and `docs/development/testing.md` (a 404 is skipped, any other error fails), plus conditional guides for protected paths, ADR changes and workflow or operations changes. It goes in the system prompt, at most 30,000 characters per file and 60,000 in total. The complete head content of every modified file (at most 60,000 characters per file and 200,000 in total) goes in the untrusted user message. Files are read as raw bytes and decoded as strict UTF-8. A file containing NUL bytes or invalid UTF-8 is binary or corrupted: it is never sent with replacement characters, it counts as omitted, and the check fails as "Insufficient context". This applies to guidance, to modified files and to a pure rename's head content alike. An added file is already in the diff, so it is not sent twice, but its raw head content is still fetched and validated the same way (not found, binary or invalid UTF-8 also fails the check), so a replacement made on the way to the diff cannot be approved. Added files do not count against the context budget. Context is sufficient only when all guidance and the complete head file of every modified file were provided without clipping. If any is omitted or clipped, the check fails as "Insufficient context" before the model is called, lists the files, and approves nothing, whatever a model could say. A test measures the real files the gate is made of (`tools/review`, the workflow and this guide, plus the trusted guidance) with the same loader: each must stay under two thirds of its limit, all gate files together under 90% of the total, so one more edit can never make a file unreviewable.
- Pull request title, description, diff and file contents are untrusted in the prompt, each inside a block delimited by a per-request random token that pull request text cannot close. This reduces, but does not remove, prompt-injection risk.

## Pull request feedback

Besides the check, the harness leaves comments so the result is visible on the pull request. They never gate anything; the check does.

- **One summary comment per review run**, found by hidden markers for the head SHA and the check run id, and authored by the App. It states the short head SHA, verdict, findings and a link to the check. A run only ever writes the comment bound to its own SHA and run id and never edits another run's or commit's comment, so no delayed, cancelled, restored or rerun review can overwrite a newer verdict. A cancelled run leaves no comment.
- **The check is completed before the comment says Passed or Requires changes.** After the review, the harness verifies the head, completes the check, and only after GitHub accepts that publishes the final comment, then appends a note about the comment to the completed check (retried once). If that update still fails, the job succeeds because the verdict is already recorded, and the job log carries a `::warning::` with the note and the status or network error. If the completion fails, the check is read back, but a read-back is only a point-in-time observation: a request that failed with a network error or a 5xx may still arrive and complete the check later. "Not completed, no verdict is recorded" is therefore written only when GitHub definitively refused every attempt (4xx) and the read-back shows the check still open. In any other case, including an open check after a transport failure or an unreadable check, the comment says "Outcome unconfirmed" and that GitHub may or may not record a verdict. Either way the job fails, and a comment never says Passed for a check that did not finish.
- **Each surface says what it omits; none is promised to be a full listing.** The comment lists the first findings that fit in about 30,000 characters (at most 30); the check text holds as many whole findings as fit in 60,000 characters. When the rest are in the check text, the comment says "more in the check". When the check text's own limit is reached, the check says how many findings it does not list, and the comment says how many are "not listed in either text". Those findings may still appear as inline review comments (at most 10 per review, blocker or major, on lines in the diff) or check annotations (at most 50, on lines in the diff), which have their own limits, so the wording never claims a finding is absent everywhere. When more than 50 findings are on lines in the diff, the check says only the first 50 are annotated. The inline review text says the summary and the check may be truncated and that the check is the gate.
- **At most 10 inline comments** in one review, only for blocker or major findings whose line is in the diff. Minor findings, findings with no location and findings outside the diff appear in the summary and the check only. A repeated run on the same commit does not repeat a comment; concurrent runs are handled as described in Limits.
- **Review event is always `COMMENT`.** The harness never sends APPROVE or REQUEST_CHANGES, never merges, and has no Contents write. A test enforces the endpoint allowlist.
- Text from the model or the pull request is escaped and length-capped before it is published; whenever text is cut, the cut is marked with the number of characters not shown ("[truncated: N more characters not shown]"). A finding message is kept whole up to 8,000 characters in the comment, the check and an inline comment, and an annotation keeps 1,000, each marked when cut. This covers comments, the check summary and details, error messages and check annotations (only on lines in the diff, at most 50, messages capped at 1000 characters). If GitHub rejects the annotations, the check is completed again without them. The summary is then recomputed from what the check actually holds: it says the annotations could not be attached and none are published, how many findings the check text lists (all, or only the first N of the total), and that the omitted findings can appear only as inline review comments. The comment says the same about annotations.
- Every comment write first confirms the pull request is open and its head is the run's SHA. A run for a commit that is no longer the head publishes no comments but still completes its own check. Duplicates for the same run are rewritten to match. Comments for other SHAs or by other authors are never read as state or modified.
- If a comment cannot be published, the check still reports the verdict and its summary says "Pull request feedback: could not be published" with the HTTP status; if that note cannot be written either, only the job log says so. A comment failure never changes the verdict.

## Changing the review mechanism

`.github/**`, `tools/review/**`, `tools/release/**` and this guide control the gate and releases; [review.mjs](../../tools/review/review.mjs) names them in the check summary. With one owner and one authoring identity, control comes from separation of keys and where code runs, not a second reviewer:

- The App signing key and gateway key live only in the `ai-review` environment (deployment branch `main` only). The authoring identity cannot read or set them, and a pull request cannot reach them.
- A pull request is always judged by the harness already on `main`, so a change to the gate cannot alter the review of itself. It takes effect only after merge.
- Before a protected-path change merges: an independent inspection by a separate reviewer (Codex) at the exact head SHA, re-done after any further commit, and the owner's explicit authorization to merge. Record both in the delivery audit.
- Branch protection, administrator enforcement and the required checks are unchanged by this guide.

## Enabling the gate (one time, in order)

1. Independent inspection of the gate pull request at its final head SHA; the owner authorizes the merge.
2. Merge the gate pull request (workflow, harness, tests, this guide). Do not require the check yet.
3. Owner enters the `ai-review` secrets and variables above.
4. Run the forgery test below on disposable branches, then a real pull request into `main`.
5. Add **Independent review** as a required check whose source is the GitHub App, not "any source".

## Forgery test (before step 5)

Any workflow on any branch with `checks: write` can post a passing check under the GitHub Actions identity onto any commit, so a requirement pinned to GitHub Actions can be forged. A requirement pinned to the App cannot be satisfied by that identity. Prove it on disposable base branches, with administrators included in the rules:

1. Base branch A requires a context pinned to GitHub Actions. From another branch, post a same-name success check with the workflow token onto a PR head. Expected: the PR becomes mergeable (baseline: the exposure is real).
2. Base branch B requires the same context pinned to the App. Repeat. Expected: the PR stays blocked and a merge attempt is refused.
3. On `main`, confirm the App's own check passes on a real PR head SHA and reports the App id and slug.
4. Confirm a branch workflow that requests `environment: ai-review` is denied, and that a new commit invalidates the earlier verdict.

Delete the disposable branches and rules afterwards.

## Limits

- The existing CI checks are pinned to the GitHub Actions identity and are, by the same mechanism, forgeable by anyone who can push a workflow. They are not protected by this gate.
- GitHub has no compare-and-swap for comments, so a run cannot safely edit a comment it did not write: a re-read before the write only narrows the window. The cost is clutter: every push and rerun leaves its own comment, labelled with its SHA and run id; a reader compares the SHA with the head and reads the check status. Concurrent creation of two comments for one run is not prevented; the concurrency group makes it unlikely. The check, not the comment, is the gate.
- If `main` moves during a run, the reviewed diff can differ from the one against the newer base.
- The compare API's truncation behaviour and the equality of the listed patch with the diff hunks are only partly verified: a captured real compare (`tools/review/fixtures`) passes and altered variants fail. A systematic mismatch would fail every PR closed.
- Listings (comments, review comments) are read up to 30 pages of 100, so 3,000 items; a listing that fills all 30 pages is treated as possibly truncated. With more than 3,000 comments the summary comment cannot be located safely, so none is written and the check says so. With more than 3,000 review comments the inline findings are still posted, but duplicates cannot be checked or removed and the check says so. The verdict is never affected.
- Inline findings are de-duplicated per commit, so a new push can repeat an inline comment for the same text. Concurrent runs of one commit can both post the same finding, because listing and posting are not atomic and cancelling a run does not stop a request already sent. Afterwards each run deletes its own copies that are not the oldest. This is best effort, not exactly-once: it relies on GitHub listing consistently, a removed copy leaves its review body behind, and a failed cleanup is reported in the check.
- Only the modified files are provided in full. A model that reviews a change whose safety depends on an unmodified file can still approve; this is disclosed, not enforced.
- Comment behaviour is tested only against a fake GitHub; the first real run confirms rendering and that the author is `lantern-independent-review[bot]`.
- Tests use a fake gateway: they prove harness logic, not model quality.
- Rotate the App key and gateway key about yearly, or at once after suspected exposure.
