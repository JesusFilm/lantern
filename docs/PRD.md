# Lantern

Lantern helps team members prepare a position focus and agree it with their career lead. The product centers on a useful conversation supported by a clear, persistent document.

## Business rules

The [review, confirmation and cycle rules](rules/review-and-confirmation.md) define current intent, exceptions and open decisions for that area. Other areas remain described below until migrated.

## Product behavior

- The application uses a geometric Lantern mark and labelled navigation icons. With `sidebar-collapse` enabled, members can collapse the desktop sidebar to an icon rail using the control above their profile at the bottom. With the same flag enabled, phones show a top-right three-bar button that opens a sliding menu panel. Selecting a destination, closing the panel, tapping outside it or pressing Escape dismisses it; keyboard focus returns to the menu button. Desktop icons stay anchored while labels fade out before the rail narrows; on expansion the labels fade in after the rail widens. Animations respect reduced-motion preferences. Destinations retain accessible names and hover labels. The choice is stored in the current browser, survives navigation and reload, and defaults to expanded when browser storage is cleared or unavailable. Storage failures do not prevent toggling for the current page. This preference does not change access or account data. The flag is enabled by default in local/stage and hidden by default in production.

- Guide → Example expands Single Example and Engineering Example as nested choices on desktop and phones, using the same submenu selection styling as other guide topics. The reading panel has no duplicate example toggle buttons.
- Guide includes a Procedures topic using the existing nested topic navigation: The year and Agree a focus. The year shows two six-month cycles with progress check-ins and end-cycle reviews. Agree a focus illustrates drafting, requesting review, discussing and agreeing, and confirmation. Confirmed content stays locked; mid-cycle amendment versus replacement and accidental-lock recovery remain undecided. These screens do not provide scheduling, automatic carryover, amendment or renewal tooling. The existing writing topics remain available.

- Position focuses is the member authoring destination for position-focus documents. Add objective offers Write myself or Guide with AI when inference is available. The choice covers one objective and its nested SMART goals. Existing objectives offer explicit manual editing or AI guidance; individual goal Add/Edit actions are compact manual shortcuts with parent context.
- Both methods edit the same pending objective. Manual authoring has only fields, type information and initiative choices; the Guide holds writing explanations. Guided authoring moves through Your work → Objective → SMART goals → Check objective using Back/Next and a cancellable loading overlay that retains the screen. Existing guidance first asks what the member wants to improve; skipping the optional question continues to goals. Existing wording is never regenerated merely by entering guidance. On Objective, Next requires an initiative or Other; correcting the selection clears the validation message immediately and retains entered work, answers, wording, type and goals. A member can switch methods without losing content.
- Save objective persists that objective and its goals once, directly to the position focus. It preserves unrelated objectives, goals, types and alignment. Partial objectives are saveable; unfinished goal plans cannot be silently omitted. Cancel and navigation warn about unsaved work. No separate suggestion acceptance, progress-save, resume or coaching-discard controls are shown.
- Contribution, Personal development and Leadership labels appear consistently in authoring and member/career-lead reading. Draft types are editable without changing wording, goals or initiative choices. AI recommendations are labelled for member confirmation; information controls explain each type. All types retain the same optional initiative selection rules.
- Existing private checkpoints are retained without an Earlier working notes interface. The authoring UI creates no separate saved coaching sessions. Confirmation retains its existing checkpoint cleanup behavior.
- Members open Review & discussion with their existing focus in a read-only review mode: title/date, objective and SMART goal editing, adding, removing and AI actions are absent. Notes and review requests remain available; Position focuses is the single return action, with an unsaved-note guard. Reopening a draft from the list restores authoring. Career leads review the submitted snapshot with the same objective cards and nested numbered goals. Check objective concerns only the pending objective and its goals. A saved focus needs a Contribution objective with at least one goal to request review or be confirmed; development-only drafts remain saveable.
- For members and career leads working on their own draft, the open review-request form stays visible when sending is unavailable. The optional note is disabled whenever Send request is disabled. A visible reason sits beside Send on desktop and above it on phones, and describes both controls to assistive technology. Missing Contribution content, sending, stale versions and already-requested versions explain how to proceed. If confirmation happens while the form remains open, it shows a locked-state explanation and preserves unsent text. Reopening a confirmed focus shows its retained discussion, when present, without a request form; see [RC-15](rules/review-and-confirmation.md#rc-15-explain-unavailable-review-and-confirmation-actions) for the source ambiguity. Saving a Contribution objective with at least one SMART goal restores readiness; sending still requires an explicit action. Notes remain optional, and a failed request retains the entered note for recovery. When a retained note is blocked and no send is in progress, Copy unsent note exposes a read-only, keyboard-selectable copy.
- Review requests preserve immutable saved snapshots. The lead's review-request view shows changes and notes, and members see the retained discussion beneath confirmed objectives. New replies are indicated and acknowledged when displayed. Eligibility, version, notes and locking rules are in [RC-01–RC-11](rules/review-and-confirmation.md).
- With `coach-redesign` enabled alongside `coach`, the authoring header labels the current method and makes the alternative an explicit Switch action. Guidance first asks for Contribution, Personal development, Leadership or Not sure. It uses the member's described work and role, the saved department mission and initiative descriptions, and the selected type's lens. Type recommendations offer an explicit switch without preselecting it. A personal interest can support development when the member explains its professional use; the coach asks when that connection is unclear.
- The redesigned coach can ask a focused question or show a concern in a labelled AI coach feedback panel during exploration, objective refinement, goal ideas or goal wording. On an objective draft, the coach can assess three Guide-based elements: the contribution, who benefits and how, and connection to mission (or to work for development and leadership). The three checks distinguish met, needs attention and uncertainty; missing or invalid assessments never imply approval. Editing the wording or type marks earlier checks stale, and members can recheck without rewriting. The coach uses only the mission configured by the career lead; when it is empty, Contribution alignment is uncertain. An implied fit does not require mission text to be repeated. The checks assess only the wording on screen; details from earlier answers count once they appear in it. After the member answers a question, the coach drafts from the answer rather than showing the original wording, unless the answers give nothing usable. Answering feedback never starts a chain of questions; remaining gaps appear as feedback beside the draft. At the goal step, a member who cannot say how success will be shown still gets an editable goal: the coach drafts from their action, or Lantern uses the action and selected date, with the gap as feedback. Empty goal ideas are requested once more before the feedback is shown. When a response lacks checks, the server requests them automatically and retries once; a failed check preserves the draft and leaves a manual check available. Once every check is met, optional refinements are left for SMART goals. The coach never invents a role, beneficiary or outcome, nor replaces an intent that does not fit with a different objective. A first Contribution draft must name who benefits in the member's own words; otherwise the coach asks who benefits instead of drafting. Members can respond to feedback and ask the coach to update their current wording, or continue without answering. Failed requests retain their draft and response. The coach drafts early when intent is clear and asks concrete questions about material gaps. After one initial follow-up, if it still cannot draft, the member can edit their own wording with the remaining question shown. A discovery objective labels what remains unknown rather than inventing facts or agreements. The coach applies the objective and SMART goal principles from the Guide without treating worked examples as member facts. Member role-type configuration remains follow-up work in [#102](https://github.com/JesusFilm/lantern/issues/102); role is currently supplied in the member's description, never inferred from an access role.
- In the redesigned flow, entering SMART goals with no existing goals requests possible actions immediately. Selecting an idea opens an editable action and date. Guided target dates start provisionally at the focus end and remain editable. They must fall inside the focus period; the server enforces this and adds the selected date to the generated goal itself, so a model cannot substitute a different deadline. Check objective displays the pending objective and goals without another model call. Members can edit a suggested objective, or go back and request another suggestion. Ordinary Back and Next preserve edits; an explicit retry requests a new draft from their original context. Existing objectives can still be brought into guidance using the Guide. Missing goals produce a visible warning but do not block saving. A failed coach call keeps the draft and offers retry or manual continuation. Coaching receives the complete current goals up to a 128,000-character context limit; larger contexts receive an explicit message to shorten the input or continue manually, without truncating or changing the draft. With `coach-redesign` off, the existing coaching flow remains available; the new review stage is hidden. The flag is on by default locally and on staging, off in production.
- Coaching uses Qwen with automatic OpenRouter/Gemini fallback, validated bounded responses, cancellation and a manual continuation path. Enabled hosting requires both provider keys. Additional repository/project context and email notifications are deferred. See [coaching operations](operations/coaching.md).

- Members create and edit their own titled, dated focuses with objectives and SMART goals. Empty and partial drafts are valid. Objectives can include Personal Development and Leadership types.
- The optional Guide starts with the draft → request review → review and agreement → confirmation process, using a responsive refinement-loop diagram instead of a repeated written walkthrough, with brief initiative-selection guidance, saved-draft visibility and confirmation locking. Separate lessons explain objectives and SMART goals. A simple onboarding example and an illustrative engineering example each show one objective and two goals with illustrative initiative badges using the team’s established icons and colours; their targets do not impose a template or cadence. The empty first-focus screen links to this introduction.
- Focuses open in a compact reading view. Objectives use a dedicated editing page; metadata and quick goal edits use compact dialogs. Writing guidance lives in the Guide, separate from the explicit AI-guided method. The Contribution objective remains `normal` in storage; Personal development and Leadership objectives are explicitly optional. Phone objective writing uses the page scroll; compact dialogs have one scrolling content region and stable Save and Cancel actions.
- Within Position Focuses, browser Back/Forward retains a pending editor and its input against the original document/version. Save writes that source and opens the saved document; Cancel reveals the navigation destination. Failed or stale saves retain input. Leaving Position Focuses or reloading the page ends the in-memory edit.
- Confirmed focuses offer Focus and Progress & notes views. The member can set or clear In progress, Achieved or Needs attention and edit one note per objective or SMART goal in a single dialog. An unset status has no badge; the action reads Add note when both fields are empty and Edit progress otherwise. Statuses also appear beside the relevant item in the Focus view. Career leads can read progress for current members in their department, but only the focus owner can write it. Progress is unavailable on drafts and is separate from locked focus content and review discussion notes. Failed saves retain the member's input.
- Career leads browse current department members and their focuses. Confirmation records who confirmed and when; cancellation and failed or stale attempts leave the focus unchanged by that attempt, with a clear message. Self-facing guidance, note labels and confirmation copy must not imply two people participated. See [review and confirmation rules](rules/review-and-confirmation.md).
- Account offers Light, Dark and System appearance. The choice is stored in the current browser; clearing browser storage returns it to System, which follows the device setting.
- Account display names persist. Career leads can add eligible registered users to their department. Rejoining former members is not currently supported.
- A career lead configures the organizational mission and strategic initiatives in Department → Mission & initiatives. Saves persist the department's configuration atomically and reject concurrent stale edits. An empty mission hides the banner; hosted departments are not automatically seeded.
- Position Focuses shows a configured mission in an always-visible editorial card, with no hide control or remembered visibility preference. The card includes the selected geometric Jesus illustration, mirrored horizontally, to the right of the mission text on desktop and below it on narrow screens. Department settings use a preview-first mission editor: a live banner sits above the mission statement, with Change image on the artwork. A blank mission hides the banner but leaves the image chooser available. Career leads can choose a PNG, JPEG or WebP, restore the default geometric illustration, or remove the artwork. The whole image fits without cropping or stretching; only the bundled default is mirrored. Image edits remain pending until Save changes and can be cancelled with other mission edits. Images persist per department with the same ownership, concurrent-edit protection and atomic save as mission text. The browser accepts files up to 10 MB and 16 million pixels and resizes them; the server validates and re-encodes bounded raster data before storage. The Position Focuses heading has no explanatory subtitle.
- The objective dialog presents initiative checkboxes beneath the objective, without search or a selected-chip field. Members can choose several active initiatives, or **Other — none of these apply**, which excludes named initiatives. Unselected initiatives remain valid in partial drafts. Objective selections persist with the focus and are visible to its member and career lead.
- Initiatives can be renamed, archived, or restored. Archived initiatives disappear from new choices; existing selections remain. Saved objectives snapshot initiative names, so later configuration edits cannot rewrite confirmed focus history. The mission provides context outside objective authoring rather than a required alignment field.
- Initiative add/edit dialogs include an optional plain-text description directly below the name, limited to 500 characters. The lead explains what the initiative means and why it matters; descriptions persist with the department configuration through the existing Save changes flow. Existing initiatives without descriptions remain valid.
- Guide includes Strategic initiatives alongside Objectives, SMART goals and Example. Selecting the topic expands active initiative names and their configured identities beneath it, using the existing nested lesson navigation. Selecting an initiative displays its name, color, icon and current description in the main reading panel. Missing descriptions, no active initiatives and failed reads have explicit states; failed reads can be retried. On phones, initiative navigation expands vertically so names remain readable. Descriptions are current department guidance, not part of saved objective snapshots or confirmed focus history.
- Department → Mission & initiatives ends its initiative table with a fixed grey Other identity. This is the existing alignment fallback, not a configured initiative: it has no status or actions and is not stored in the initiatives array. The previous multiple-selection and Other/archive explanatory paragraphs are omitted; configured initiatives retain Active/Archived status and Edit/Archive/Restore actions.
- Initiative add/edit dialogs offer a quick palette of twelve predefined SVG icons and eight distinct preset colors (red, orange, yellow, green, blue, purple, pink and slate). There is no SVG upload or custom color picker; new appearance writes are restricted to the presets. Previously saved custom appearances can be retained unchanged or replaced with presets. The list, objective choices and saved alignment badges show the configured identity alongside its name. Appearance is optional for existing initiatives and can be cleared. Newly saved objectives snapshot appearance from department configuration alongside names; confirmed documents and old documents without appearance are not rewritten. Dialog updates remain pending until the department panel's Save changes action succeeds.
- The optional post-deployment [initiative setup script](../tools/database/seed-initiative-appearance.sql) adds the four agreed initiatives and their approved descriptions if missing and assigns pink/heart, blue/light bulb, green/sprout and yellow/people, matching Engineering’s staging configuration. The separate [description-only script](../tools/database/update-initiative-descriptions.sql) updates existing descriptions while preserving configured appearances. It targets an explicitly chosen department and preserves existing IDs, mission, archive status and focus history.

- With `LANTERN_ENV=local`, synthetic local access and a loopback database, startup fills a new synthetic account’s active department with the shared synthetic mission and the four known initiatives, their approved descriptions and staging appearances. Repeated startup preserves IDs, order, archive status, existing appearances, mission, extra initiatives and saved focuses. It fills missing appearances and absent description fields but does not reset local edits, restore removed membership or seed hosted environments.

## Desktop and mobile support

Lantern supports desktop and mobile browsers. Preserve the desktop composition;
phone layouts prioritize the member's immediate task, not simply stacked panels.
On phones:

- Show one objective and its goals at a time. For multiple objectives, provide
  swipe, Previous/Next, a direct chooser and optional full-document reading.
  Keep navigation reachable during long reads. Dates/status details are available
  on demand, and document records precede mission context.
- Keep Guide topic/lesson choices compact, with persistent progression controls.
  Example choices reveal their content. Swipe has tap and keyboard alternatives;
  long content scrolls freely without forced vertical snapping or auto-advance.
- Use full-screen objective/goal writing with stable Save/Cancel and one content
  scroll area. Preserve input and the existing source-bound editing behavior.
- Support 320 CSS pixels and short landscape: wrap prose, stack simple records,
  constrain artwork, keep standalone touch targets at least 44px and form text
  at least 16px. Do not conceal broken reflow with page-level overflow clipping.

Apply the [responsive review checklist](development/testing.md#responsive-ui-review)
to UI work. Native apps and offline operation are outside this decision.

## Access and data

Hosted access uses Jesus Film sign-in and server-issued sessions. The server checks the session on application document requests and redirects signed-out visitors before sending the app HTML or loading screen. Authentication uses prompt=login, requesting a fresh login at Auth. The redirect also works with JavaScript disabled. Ordinary valid Lantern sessions remain signed in; a coordinated identity cutover invalidates existing sessions and requires fresh JFP One sign-in. Failed or cancelled authentication shows an explicit retry screen instead of automatically looping; unavailable authentication shows its configuration state. An existing email held by a different sign-in identity requires administrative recovery; sign-in never creates another same-email account or transfers access automatically. Unresolved duplicate accounts are marked Account repair required in Add user and cannot gain membership. Recovery preserves the original account, department, role and focuses, and removes only a verified empty duplicate. Admission requires an exact approved email, with no domain restriction in any environment. Active department membership and server-assigned roles determine access. Members cannot read another member's focuses; career leads can read and confirm focuses within their department, but cannot edit another member's draft.

See [People and access](../GLOSSARY.md#people-and-access) for the account, approval, membership and career-lead relationships. A manager does not automatically gain access through their job title; application permissions come from active membership and role.

The configured owner can open a read-only feature flag page after signing in with an active department membership. It shows each registered flag's state for the current environment, without listing preview accounts. Other accounts cannot open the page; flags remain controlled through environment settings. In explicitly enabled local access, the synthetic local account uses the same owner-email and membership checks without signing in.

PostgreSQL stores account, membership and focus data. Saves detect concurrent edits. Ending membership removes access while preserving department-scoped history. Local access is explicitly configured and disabled by default.

## Delivery and scope

Staging receives application and schema changes automatically after a PR merges to main. An opt-in authenticated acceptance journey exercises the deployed build with disposable synthetic accounts and ordinary sessions, without a public login bypass. After hosted rehearsal, the owner may enable automatic production promotion of the latest main SHA with successful CI, readiness, authenticated acceptance and cleanup from the same run. Automatic promotion requires matching advertised staging/production schema versions; schema-changing releases remain manual. Manual promotion of a selected full main SHA remains available. Migrations and the application deploy from that same revision. See [Testing](development/testing.md) for coverage and limits, [Releasing](operations/releasing.md) for operator steps, and the README for provisioning and configuration.

Current work prioritizes reliable delivery and a usable hosted product. New product scope is chosen directly by the owner. The [cycle rules and deferred decisions](rules/review-and-confirmation.md#open-and-deferred-decisions) describe the agreed rhythm and unresolved mid-cycle changes. Notifications, dashboards, and administration beyond the planned scope below need a separate product decision before implementation.

## Planned owner administration API

This section is agreed product scope, not delivered behavior. The first API-first
increment lets an owner set up departments and career leads through a versioned
HTTP API and an MCP server. It publishes an OpenAPI description; an interactive
API page, a full CLI, and member-facing focus operations are deferred. An agent
may perform the requested administrative actions on the owner's behalf without
an additional confirmation for each write.

### Owners and access

- `LANTERN_FLAG_OWNER_EMAIL` will accept a comma-separated list of exact,
  normalized email addresses; an existing single-email value continues to work.
  The same list controls owner API access and the existing feature-flag page.
  That page retains its approved, signed-in account and active-membership checks.
- An active, verified human JFP One identity and a Lantern owner-list match authorize all
  administrative API operations. An owner needs neither ordinary Lantern email
  approval nor department membership to administer Lantern. There is one owner
  role, with no separate administrative or audit policies. Owner status alone
  does not grant focus, review-note or coaching-data access.
- An owner can assign themselves as career lead; that separate role grants the
  usual access to current members' focuses in that department. Assignments are
  audited. An owner-list change takes effect when the updated environment is
  serving; revoking a JFP One session alone may take until token expiry to affect
  an already issued token.

### Departments, accounts and membership

- Owners can list, create and view departments, list their members, find
  registered accounts by email, add eligible registered accounts as members,
  assign or replace a career lead, demote a lead to member, and list or add
  approved sign-in emails. Approval can precede the person's first sign-in.
- An account search returns name, email, account ID and membership status.
  Assignments target a specific registered account. When an email matches multiple
  Lantern accounts, do not silently choose or link them; resolve the ambiguity.
  Existing account linking and sign-in behavior do not change.
- A department may have no lead, but at most one active career lead. Assignment
  adds an eligible registered person with no membership or promotes an active
  member of that department. Replacing the lead is atomic: the former lead
  remains an ordinary member. Demotion also preserves membership and history.
  Reject other-department and former memberships; transfers and rejoining remain
  unsupported. Active department names are unique ignoring case and surrounding
  whitespace.
- Deleting departments, removing members and revoking email approval are outside
  this API increment. Existing administration commands remain available.

### Operations and audit

Record successful administrative reads and writes and denied attempts in PostgreSQL, including the
actor, action, target, outcome, time and calling client when available, without
bearer tokens or request secrets. A successful mutation and its audit record commit
together; record denials where possible. Retain records for 90 days using existing
trusted database access. Apply configurable rate limits before enabling the API.
New behavior follows the feature-flag and release procedures.

The agreed routes, technical boundaries, phases and verification requirements are
in [owner administration API plan](plans/owner-administration-api.md).

## Weekly goals and daily updates

**My week** is behind `weekly-updates` (hidden by default in production). Weekly editing routes remain private to their author, including for career leads. **My team**, behind the separate `team-updates` flag, lets active members read dated updates and goal snapshots from active members of their own department. Both flags default to hidden in production.

A week starts on Monday and runs through Sunday, identified by calendar dates. Weekly goals are due at the end of the selected week; there is no separate per-goal deadline. My week opens on the current week as one editable page: draggable goal cards above the daily update composer. Goal titles can be edited inline, and a three-dot menu on the right of each card provides **Add link**, **Edit details**, and **Delete** without switching sections. Links occupy one horizontally scrollable row in goal cards and team updates. Existing links remain editable on the card; the separate action row is removed. There are no goal completion checkboxes; each card uses the daily status controls in its full-width footer. **Add goal** in the main heading appends a goal. Goals, daily text and statuses save automatically in the background after a short pause. Statuses stay associated with a goal's stable identity when adding, renaming or reordering goals. The displayed date range runs Monday–Friday, showing the year only for dates outside the current year. The date range and previous-week and next-week arrows form one compact, joined button group. Clicking the middle date range returns to the current week. Members can browse from their earliest saved week and move forward to plan future weeks. The previous arrow is disabled at the earliest saved week (or the current week when there is no earlier history); the next arrow remains available for planning ahead. Each arrow moves one week, including between future weeks. Navigation asks before discarding unsaved daily edits. Historical links still open their saved week.

Weekly goals may be tasks or outcomes; guidance encourages a clear intended result, such as “Run the pre-release smoke test and record the results.” They do not repeat automatically. Behind `weekly-goal-copy`, **Copy last week’s goals** reads the selected week's immediately preceding calendar week through the existing private weekly API and appends its latest goals to the current draft, replacing only pristine empty writing rows. It copies titles, descriptions and work links with fresh goal identities and completion cleared; statuses and daily updates are not copied. Existing goals and historical records remain unchanged. Empty source weeks, read failures and exceeding the ten-goal limit have explicit messages that retain the draft. Normal autosave persists the copied goals and offers its existing retry on failure. This browser control uses the existing authenticated, `weekly-updates`-guarded read/save routes and adds no API route. The `weekly-goal-copy` control is hidden in production until released, and requires `weekly-updates` as well.

Members keep 1–10 goals of up to 1,000 characters each. Complete goals save automatically; failed saves retain edits and offer a retry. Removing a goal requires a modal confirmation with an explicit warning that there is no undo. Saving a changed plan adds a version; the original and all later plans remain available. A stale version is rejected without replacing saved history. Revision numbers stay internal; history presents original and updated weekly goals without technical version labels.

The Link button opens a full-screen picker with a close X at the top right; its size stays fixed while changing work types. Each weekly goal can optionally link to up to five pieces of work: one of the member's saved position focuses, or named HTTP/HTTPS links for projects, repositories, issues and other work. Focus choices are resolved against the member's active department and ownership; saved history retains the trusted focus title at that time. External links have a name of 1–200 characters and URL of up to 2,048 characters, without embedded credentials. Links appear alongside goals in daily updates and plan history. Editing or removing links preserves earlier plans. Goals have server-issued identities that survive edits and reordering, so later integrations can target a particular goal. Members can save their GitHub username in Account. This personal preference prioritises assigned or mentioned issues, repositories they are involved with or committed to in the last 30 days, and related projects in the work picker. Results explain their relevance; ordinary browsing remains available when activity cannot be fetched. A username changes ordering only and grants no GitHub or Lantern access. Behind `weekly-focus-links`, confirmed focuses also offer objective or SMART-goal targets, identified by their locked focus version and positions. Draft links remain whole-focus links. The focus shows linked weekly work to its owner and career lead, respecting goal visibility. Daily On track suggests In progress, At risk or Blocked suggests Needs attention, and Done suggests Achieved. The owner reviews the suggested status and explicitly saves it through the progress editor; Cancel makes no change. Whole-focus links do not suggest a specific target. External completion events and automatic goal-state changes remain future work.

After saving a plan, a member can write today’s daily update of up to 4,000 characters and mark goals **On track**, **At risk**, **Blocked**, or **Done**. New goals, including the initial empty writing row, have no status selected. Existing goals begin a new day with statuses unselected. Members explicitly choose each status; planning a future week does not create a daily update, and status controls are disabled outside the current week. The borderless text area grows with its content, without visible editor headings. Text and status changes save automatically after a short pause; partial statuses and cleared text are allowed. The update field sits below the goal statuses with only a short placeholder when empty. Autosave always targets today and maintains one displayed entry for that date. Daily entries appear newest first with equal spacing and matching card styling. Today’s dated section stays open and editable, without a collapse control, after saving or reloading, with current goal titles, order and statuses reflected immediately. Further changes replace that day’s displayed entry rather than adding another. Past saved days remain readable in their own collapsed entries, showing goal text and statuses from the plan at save time with the same goal rows and status pills as today. Previous internal revisions and plan versions are retained. Historical week views cannot create an update for a different day. Failed saves retain the draft with a retry action, and leaving with unsaved input asks before discarding it. A stale plan requires reloading before submission. Done is recorded as the daily status and dims and strikes through the goal title.

Identity and active department membership are resolved by the server. Records belong to that member and department; ending membership denies access and preserves history. The browser's calendar determines the initial week and update date; the selected date is explicit. Structured achievement outcomes, completion automation and Slack/MCP integrations remain future work. Confirmation of a focus continues to mean agreement, not achievement.


### Weekly visibility

Behind `weekly-goal-privacy`, each goal offers Team (default), Me and my career lead, or Only me. Team viewers see only team goals; career leads can also see lead-shared goals, and owners can see all their own goals. The bearer Team API and TV expose only team goals, regardless of the token creator's role. Filtering includes descriptions, focus titles, work links and goal statuses. Historical daily snapshots must satisfy both their original visibility and the goal's most recently saved visibility in that week, including removed goals. Disabling the choices does not remove filtering or widen saved visibility. Copies retain privacy choices. If sharing controls are unavailable, copying restricted goals is refused without changing the current week; it never widens their visibility. Similarly, copying specific focus targets requires the target controls to be available. Daily update bodies always remain visible to the department and TV; My week states this explicitly. Authors should keep private details out of daily update text. Sharing a team-visible goal also shares its linked focus title and target labels, without granting access to the focus itself.

Saved focus drafts, including personal-development objectives, retain their current owner-and-career-lead visibility and whole-focus review. Changes to personal-development approval or privacy remain deferred pending an owner decision (#206).

### Team daily view

My team opens on the browser’s current calendar day. A joined date control provides previous/next-day navigation; the centre returns to today. Forward navigation stops at today and backward navigation stops at the earliest update from the active team. Each member card shows their name, optional GitHub profile and avatar (initials when unlinked or unavailable), weekly goals, status pills, supporting work links and that date’s latest update. Goal wording comes from the plan version saved with the update; members without an update show their current plan for that week and “No update yet”. The view has no editing or membership controls. Loading failures offer a retry. Each member’s picture, name and GitHub handle sit immediately above their card. Desktop cards show goals and update in aligned columns; narrower screens stack the sections.

Team and TV profile pictures use authenticated Lantern image URLs. The server fetches linked team avatars from GitHub once, converts them to WebP and caches them on disk, so clients need no external internet access. Cached pictures survive server restarts; uncached or unavailable pictures retain the initials fallback.

Account → Team API access, behind `team-api` and `team-updates`, lets active members create named read-only integration tokens for their own department, reveal the full token once, and revoke their own tokens. Tokens expire after 90 days and stop working when approval or original department membership ends. A separate TV application can read dated team snapshots and cached pictures using the versioned bearer API; tokens cannot edit data or manage credentials. See [the API contract](development/team-api.md).

The TV dashboard is owned and built by the separate office-tv-controller application. Lantern supplies its versioned read-only team API; the controller keeps the bearer token on its backend and proxies data and pictures to the offline TV.

The server resolves the reader and active department membership. It selects only active peers in that department and never accepts client-provided member or department scope. Ending membership removes access and excludes that person from the current team roster while retaining their stored history. The team route and navigation are unavailable when `team-updates` is hidden.

### Unread review activity

Behind `review-activity`, career leads see a count of focuses with unopened review requests or unread review-discussion notes from other authors. The list marks these focuses New. Opening a review acknowledges the exact displayed request and displayed notes; acknowledgements persist across reloads. Own requests and notes do not create unread activity for their author. Counts are department-scoped and require active memberships. Failed loads retain the last count and offer retry; failed acknowledgements remain retryable. Progress activity notifications remain deferred.
